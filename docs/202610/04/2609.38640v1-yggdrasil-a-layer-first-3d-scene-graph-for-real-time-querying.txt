# Yggdrasil: a Layer-First 3D Scene Graph for Real-Time Querying 

Arshia Akhavan 1, Ermanno Bartoli 2, Afnan Algharbi 1,Alireza Hoseinpur 3, Iolanda Leite 2, and Bryan Donyanavard 1

Abstract — Robotic agents use 3D scene graphs (3DSG) to perform tasks ranging from scene understanding to scene interaction. Although an extensive body of work addresses scene graph generation, little attention has been paid to optimizing the graph for consumption, which leaves state-of-the-art perception pipelines to work around their own scene graph and to pay a latency cost that does not fit the real-time budget a perception loop runs on. We present Y GGDRASIL , the first 3D scene graph designed to be efficient for both generation and consumption: a layer-first hierarchical graph built from generic nodes, edges, and layers, which expresses the representations existing pipelines already produce, indoor or outdoor, flat or hierarchical, while natively answering the positional and semantic queries downstream tasks issue. Against a published DSG baseline, YGGDRASIL answers queries up to 121 × faster, and every query we measure falls between 2 and 127 μs, three to five orders of magnitude inside the 200 ms keyframe budget a 3DSG consumer lives in, on both a workstation and embedded class device. We integrate YGGDRASIL into three published pipelines spanning human trajectory prediction, object-goal navigation, and human-aware motion planning, where it removes up to 99% of the time each spends on its scene graph. The implementation, benchmark harness, and all three integrations are available online [1]. 

Index Terms —3D scene graph, spatial perception, robotic perception, hierarchical representation, spatial indexing, query processing, SLAM. I. I NTRODUCTION 

Robots operating in real environments must build a model of their surroundings and interrogate it fast enough to act on what they find. That model draws on the geometric maps produced by SLAM pipelines [2] and the semantic content associated with them [3], and the structure holding all of it together is commonly called a 3D scene graph (3DSG) [4]. A 3DSG sits between two very different halves of the pipeline: upstream , a construction stage that populates 3DSG from raw sensor data, and downstream , applications that consume it to plan, navigate, or answer questions about the scene. 3DSG’s purpose is to hand the downstream task actionable information [4], [5], a contract expressed in practice as the queries that application runs against it, such as the nearest object, the observable sub-scene, the objects carrying a given label, and the shortest path query.

A large body of work addresses the upstream side [6]– [9], designing representations that perception pipelines can populate accurately and in real time. Far less attention has gone to the downstream, where the graph would have to be designed around the queries and information retrieval. Downstream pipelines therefore have to route around their scene graph. Some serialize it for a language model to delegate the query [10], which works but is slow relative to the control loop [11], [12] and can face a context win-dow bottleneck for large scenes [13], [14]. Others keep the query algorithmic but re-materialize the graph inside a general-purpose library such as NetworkX [15] and query the copy [16], [17]. That presumes an immutable graph: when the scene is updated while navigation or planning runs, the conversion is re-paid on every frame, and the copy discards the layering and grounding that distinguish a 3DSG from a generic graph. Both are workarounds for the same missing piece, a scene graph that serves upstream construction while natively answering what downstream robotics asks of it. Recent work has begun to name the gap [18] and to propose exposing 3DSGs through a structured query interface for tool-augmented reasoning [19]; we pursue that goal one level lower, at the storage substrate, so that constructors and consumers share a single queryable graph instead of each building its own. This paper contributes: 1) A scene graph designed for consumption , in which the layer hierarchy is a directed acyclic graph rather than a stack, paired with a query API spanning pat-tern matching, nearest neighbour, field of view, and traversal, backed by per-layer and per-node spatial in-dexes that Y GGDRASIL maintains automatically (Sec-tions III, IV). 2) Three integrations spanning the perception pipeline , in published tools for human trajectory prediction, object-goal navigation, and human-aware motion planning, covering diverse use cases such as: downstream-only use, construction and consumption together inside a control loop, and augmentation of an existing graph (Section VI). II. R ELATED WORK AND BACKGROUND 

A. 3D Scene Graphs: Definitions, Hierarchy, and Layering 

Although no single definition of a 3DSG is universally agreed upon [6], [20], the term consistently denotes the stor-age backbone of a perception pipeline. A recent survey [20] unifies the competing formulations as sets of nodes and edges plus a grounding that anchors each node to the metric map, 

feature maps that attach arbitrary attributes, and an optional 

labeling function sorting nodes into hierarchical layers . A graph lacking the labeling function is considered flat. In a 3DSG, nodes are spatial concepts, most often objects, and edges are the relationships between them [20]. Nodes carry geometric attributes (centroid, bounding box, shape) and semantic ones (labels, materials, embeddings). Flat de-signs such as the 3D semantic scene graph (3DSSG) [7] and ConceptGraphs [21] stop there and invest in richer attributes, whereas hierarchical ones add layers of increasing abstraction, commonly geometry → objects → places →

rooms → building [4], [22]–[24]. Hierarchy both mirrors the human mental model of an environment [25], [26] and aids inference by narrowing the search span along ancestry [27], since an object in one room need not be sought among those of another. Within this family, the DSG line [9], [22], [25], [27] adds dynamic entities such as humans, S-Graphs [23], [26], [28] couples the hierarchy to SLAM optimization, and OpenGraph [29] adapts the layering to large-scale outdoor 

environments. 

B. Scene Graph Construction and Consumption 

Work on 3DSGs falls into two threads. Construction (upstream) , called generation in robotics and learning in computer vision [20], builds the graph from sensor data, and spans learned semantic prediction from point clouds and RGB-D [7], [8], open-vocabulary variants [21], [30], and real-time, SLAM-coupled construction of layered graphs [9], [29], [31]; its output is the graph itself. Consumption (downstream) instead uses an existing graph to solve a task: embodied question answering (GraphEQA [32]), LLM-based task and motion planning (SayPlan [10], Taskography [33], DELTA [34]), object-goal navigation (SG-Nav [35], HOV-SG [24], OSG [16]), and predictive or interactive tasks such as human-trajectory prediction [17] and interactive object search [36]. Neither thread designs the store around the queries run against it. Y GGDRASIL does, and answers them in place rather than from a converted copy. III. C ORE DESIGN 

YGGDRASIL is a layer-first hierarchical 3D scene graph built from generic nodes, edges, and layers. Because none of the three is bound to a predefined vocabulary, a single YGGDRASIL graph can express the representations that ex-isting pipelines already produce, indoor or outdoor, flat or hierarchical, while still scoping a query to a single room. Architecturally, Y GGDRASIL is a cluster of graphs. Each graph is a layer , and the layers together form a directed acyclic graph (DAG). Layers are almost pairwise isolated, in that no edge joins nodes from different layers; the single exception is the nesting relationship described below. Each layer represents one level of abstraction over the entire scene and holds one kind of information: a physical layer may carry positional data, a semantic layer the attributes of each object, and a human-interaction layer only the interactions taking place between the people in the scene. Nodes represent different aspects of an object, ranging from physical representations such as a point in a point cloud or a surface in a mesh, to semantic ones such as its type. Edges represent a relationship between two abstractions: an edge between the physical nodes of a human and a mug might encode closeness , while an edge between their semantic nodes might encode an action such as holding .Where two layers share a directed edge in the DAG, the source layer encompasses the destination and sits at a higher level of abstraction. This licenses the one cross-layer relation Y GGDRASIL admits: node n1 in layer l1 may nest 

node n2 in layer l2 exactly when l1 encompasses l2 .Some form of nesting appears in every 3D scene graph that exposes hierarchy through layers [22]. What distinguishes YGGDRASIL is that prior work treats the layer hierarchy as a stack , with l1 the parent of l2 , l2 the parent of l3 , and so on, whereas Y GGDRASIL ’s DAG lets a layer parent more than one child. This matters most where a stack cannot express the scene at all. In outdoor graphs two layers often cannot be ranked, because neither stands above the other. OpenGraph [29] keeps one layer for the road lane graph and another for object instances; under a stack schema one of them must be placed above the other even though no parent-child relationship holds between a lane and an object. Y GGDRASIL ’s DAG materializes the true relationship by letting both descend from a common parent, which in OpenGraph’s case is the segment layer that partitions the environment by lane connectivity. The same freedom pays off indoors in two further ways, both of which Section V quantifies. Objects that are categor-ically the same but semantically distinct can be separated: the same level of abstraction for objects in different rooms can live in one layer per room, so that an object in one room need never be compared against nodes in another and a query’s search span is bounded by the room rather than by the building. The finer granularity also means more layers holding fewer nodes each, which shortens query time [27] and admits layer-specific optimizations that a single, heavily populated layer cannot support: because Y GGDRASIL builds indexes per layer and per node rather than globally, afrequently queried room can be indexed on its own. A single scene captures all three. Consider an office with one inventory room, where positional queries and object detection matter, and meeting rooms where they do not. A conventional hierarchical 3DSG models the whole office’s physical extent in one layer; Y GGDRASIL can give each room’s point cloud a layer of its own, so object detection in the inventory is constrained to the inventory’s objects rather than the entire building. And knowing that the inventory is queried often, one can pay a small memory price there for faster queries, which was previously unavailable because the cost of such an optimization scaled with the physical layer of every object in the building. Two derived notions recur throughout the paper. The 

sub-scene graph over a node set N of a scene graph sg 

is the graph containing every node in N, all edges and nesting relations among them, and all layers of sg , retained even when empty, since preserving the layers matters for operations such as merging and conflict resolution. The sub-tree of a node is then the sub-scene graph over the nodes nested under it, directly or through a chain of nesting, and usually captures an entire object across levels of abstraction: in Fig. 1, the sub-tree of Room 1 holds the room and every object in it. Nodes are generic in that, unlike scene graph technologies offering a fixed set of node types [16], [17], [22], they can encode any kind of information: each carries a list of features and an optional field for geometric coordinates . A node may also track its bounding box , the smallest axis-aligned cuboid containing every coordinate in its sub-tree, which is useful for quick spatial estimates and is relied upon by several downstream applications [21], [37]. Bounding boxes are disabled by default, because Y GGDRASIL keeps every enabled box current as the graph changes, so enabling one costs a small penalty on each update within that node’s sub-tree. Edges are generic in the same sense, bound to no predefined vocabulary, directed, and carrying the source and destination of the relation they encode. IV. Q UERY API S

YGGDRASIL comes with a rich set of semantic and spatial queries suited to the variety of scenarios downstream applications present. 

A. Pattern Matching 

Each node carries a set of features, essentially key-value pairs, while each edge carries a source, a des-tination, and a description of the relationship between the two. YGGDRASIL exposes nodes_matching and 

nodes_having to retrieve nodes by a specific list of features or by feature keys alone, and edges_from ,

edges_to , and edges_matching to filter edges on any of those three attributes. Every one of these queries can be run either over the entire scene graph or over a single layer. 

B. Spatial and Traversal Queries 

The nearest-neighbor family, central to navigation and path planning, comes in three flavors: nearest_nodes 

returns at most m nodes closest to a given coordinate c,

nodes_within_radius restricts those to the ones lying within a radius r of c, and nearest_in_subtree re-stricts them instead to the sub-tree of a root node r. The first two run over the whole scene graph or over a single layer, while the third is an inter-layer query by definition and so runs only over the graph. Because these queries are issued frequently, Y GGDRASIL 

can build indexes for them, trading memory for runtime. Layer-level indexing tracks every coordinate stored in a frequently queried layer and serves the first two flavors, while node-level indexing tracks the coordinates in a node’s sub-tree and serves the third. Y GGDRASIL maintains these indexes itself and updates them whenever the graph changes in a way that concerns them, which is also why enabling one imposes a small runtime penalty on updates. Both are backed by a kd-tree [38], [39]. The field-of-view query serves downstream tasks that perform traversal or object detection. Given an observer, YGGDRASIL runs a fast frustum check over the nodes lying in the sub-tree of a root node r, which lets a caller confine the result to the room an agent currently occupies rather than the whole scene. Where node-level indexing is available, the executor opts into the index-based implementation. Beyond these scene-graph–specific queries, Y GGDRASIL 

supports ordinary graph traversal and allows any standard algorithm, such as shortest path or breadth- and depth-first search, to be run over the graph. It also exposes a subgraph 

query, which returns the subgraph rooted at a given node r.V. E VALUATION

The evaluation is an ablation ladder : each target adds one Y GGDRASIL feature to the one before it, so that implementation, layer-first design, and live spatial indexes can be credited separately, along with what each of them costs in memory.

B. Targets 

The evaluation uses five targets: the published baseline, and four ports into Y GGDRASIL that each differ from their predecessor in a single respect. 1) dsg : the baseline scene graph as provided by the office dataset. Its scene consists of four semantic layers, hold-ing objects and agents, places and structures, rooms, and the building, together with a mesh array that holds the mesh representation of the entire scene outside the scene graph. 2) vanilla : the naive port of DSG into YGGDRASIL ,with no change to the internal design of the scene graph, which isolates Y GGDRASIL ’s non-architectural differences such as implementation language (DSG’s C++ against Y GGDRASIL ’s Rust) and other runtime factors. Since Y GGDRASIL is a single scene graph, DSG’s separate mesh array could not be ported; we instead gave each object a node in a mesh layer holding its mesh group. 3) chocolate : the smart port, in which we redesign the scene graph into a YGGDRASIL -friendlier one (Fig. 2), and which therefore isolates the benefit of YGGDRASIL ’s new concepts, namely the DAG of layers and the finer node hierarchy. Because practical queries are typically scoped to a single room, and because the unclaimed mesh of Section V-A adds noise to queries that should retrieve objects, we allocate four layers per room: room , claimed-object , claimed-mesh , and unclaimed-mesh . Each room layer holds two nodes, claimed and unclaimed , both nested under that room’s node in the building layer. Unclaimed meshes go into the unclaimed-mesh layer, nested under the 

unclaimed node of their room, while objects go into 

claimed-object under the claimed node, each nesting its own mesh node in claimed-mesh . The building layer is unchanged from vanilla and dsg .4) mint : structurally identical to chocolate , differing only in that indexes are enabled, node indexing for each object’s semantic node and layer indexing for each room’s claimed-mesh layer. This target isolates the benefit of Y GGDRASIL ’s live spatial indexes. 5) saffron : inherits mint and differs only in the granularity of the physical layer, giving every point of the mesh its own node rather than one node holding an object’s whole mesh array. This isolates the cost of a fine-grained physical representation. 

C. Query Workload 

We run three families of queries (Q1-3), with several flavors within each, to expose the trade-offs that come with each implementation. Every spatial query is issued from 64 reference points per room, drawn from a fixed seed, for each of the nine rooms. Throughout, dsg and vanilla use the brute-force implementation, scanning every candidate in scope, while chocolate , mint , and saffron call the corresponding YGGDRASIL API scoped to the room the reference point falls in, which the index serves on mint and saffron . On all 576 spatial queries per configuration, all Y GGDRASIL ’s flavors return exactly the answer the dsg returns, so the latencies below compare identical results. D. Experimental Setup 

Experiments were run on two platforms: a 32-core AMD Ryzen Threadripper PRO 3975WX workstation with 251 GiB of memory, and an NVIDIA Jetson Orin Nano Super devel-oper kit with six Arm Cortex-A78AE cores and 7.4 GiB of unified memory in the uncapped MAXN_SUPER power mode. Each query is run five times on each machine for each target and we report the average.

F. Discussion 

Table I shows what each rung costs to hold. vanilla is not only faster than dsg but also 36% smaller, and chocolate ’s per-room layer stacks still fit below the dsg baseline at 33.7 MB. The two features that do cost memory are the live indexes, which add 37.2 MB to mint over chocolate , and 

saffron ’s point-level physical layer, which brings the total to 144.6 MB, 3.6 × the dsg baseline. Aside from vanilla , an ablation baseline, the three remain-ing Y GGDRASIL implementations answer queries well inside the real-time bounds of state-of-the-art perception pipelines. Systems that run end to end, from raw sensor data through to a downstream task, report explicit cycle budgets. Hydra, which builds a 3DSG online from RGB-D data, targets keyframe rate (5 Hz), which as its authors state “implies a limit of 200 ms for any of these processes” [27]; on an Nvidia Xavier NX, and on the same uHumans2 office scene we evaluate on, it reports 75 ± 35 ms for objects, 33 ± 6 ms for places, and 55 ±41 ms for rooms [9]. Kimera reports per-frame meshes in under 20 ms and a global metric-semantic mesh at roughly 0.1 s per keyframe [25]. Among systems whose graph feeds a downstream task directly, S-Graphs+ reports a 74–263 ms back-end while driving navigation [28], which S-Graphs 2.0 brings down to an average of 34 ms [26], and Clio builds a task-driven 3DSG at 0.26–0.31 s per frame on a laptop carried by a quadruped [37]. On the pure SLAM side, the tracking thread of ORB-SLAM2 runs in 26–49 ms per frame [42] and that of ORB-SLAM3 in 22–33 ms, the latter reporting that it “is able to run in real time at 30-40 frames and at 3-6 keyframes per second” with a mapping thread that takes 159–267 ms per keyframe [43]. Two budgets therefore bound the space these numbers describe, the 25 ms per-frame budget of a SLAM front end and the 200 ms keyframe period in which a 3DSG consumer actually lives. Every query we measure on chocolate , mint ,and saffron falls between 2.06 μ s and 126.3 μ s, which is two to five orders of magnitude below either figure. We integrated Y GGDRASIL into three published robotic and perception projects. The three span the perception pipeline rather than one side of it. LP2 is purely downstream, reading a graph that is built once and never changes. OSG exercises both halves at once, constructing its graph and querying it inside the same loop that chooses the robot’s next action. S3DSG sits between them, overlaying a second, human-centric layer onto a graph that already exists and then querying the result. They differ equally in what Y GGDRASIL 

displaces: the conversion step in LP2, the entire store in OSG, and a hand-rolled family of spatial indexes in S3DSG. In each project we replaced only the scene-graph inter-action and left the application logic untouched, then ran both configurations so that the Y GGDRASIL version could be checked against the original. What that check can consist of differs with the project, and we report it in each; what we are after is the performance difference, that is, how much computation a scene graph designed for consumption removes from a pipeline that was not built around one. 

A. LP2: Long-Term Human Trajectory Prediction 

LP2 [17] predicts a distribution over a person’s position up to 60 seconds ahead, using an LLM to guess upcoming human-object interactions and a 3D scene graph to ground them in space. It only ever reads its graph, making it the clean downstream case. 

a) Setup : LP2 ships with two scenes: the office graph used in Section V, with 45 trajectories, and a home graph of 861 waypoints, 110 objects, and 31 trajectories. We compare its original backend, a mix of DSG [22], [27] and NetworkX [15], against an Y GGDRASIL one. Because LP2 queries an LLM internally, we recorded every response from 

gpt-5.6-luna [46] on a first run so that later runs replay them rather than calling a live model, and each configuration then runs five times per scene. Correctness holds at all three levels we check: Y GGDRASIL stores every node, edge, and relation the original does, the two variants produce byte-identical LLM prompts, and the predicted trajectory distributions match on every run. 

b) Performance : Overall, Y GGDRASIL removes 99.6% of the time LP2 spends on its scene graph in the office scene and 98.8% in the home scene (Table II). Two distinct factors account for it. The first is query runtime. The clearest case is the waypoint-to-room query, which at over 1.7 M calls on the office scene is by a wide margin the most frequent in the pipeline, and which Y GGDRASIL answers 873 × faster there and 636 × faster on the home scene. C. S3DSG: Social 3D Scene Graphs for Human-Aware Rea-soning 

Social 3D Scene Graphs (S3DSG) [48] augment a con-ventional 3DSG with humans and the activities relating them to objects and to one another. The resulting graph answers spatial, activity, and functional queries, and drives a socially-aware motion-planning task in which an identified interaction between two people becomes a cost field the planner must avoid crossing. S3DSG overlays a second, human-centric layer of nodes and activity edges onto an already-populated 3DSG, precisely the kind of layer YGGDRASIL is designed to add without disturbing the ones beneath it (Section III). Its three query categories map onto YGGDRASIL ’s API directly: spatial queries to nearest_nodes 

and nodes_within_radius , activity queries to 

edges_matching and nodes_having , and occlusion estimator with Y GGDRASIL ’s field-of-view query.

Because Y GGDRASIL ’s metric data is partitioned by layer, one index per layer suffices and a query descends a single tree, whereas the original, whose indexes are keyed by object, must probe one tree per object and reduce the answers to a minimum, so its cost grows with the number of indexed objects while Y GGDRASIL ’s does not. The margin is modest, and deliberately so. S3DSG is the case in which the original already does by hand what YGGDRASIL does internally, maintaining a family of kd-tree indexes over the metric data and keeping them in step with the scene. It is thus close to the best an external, hand-rolled indexing layer can do, and a large speedup was never the outcome to expect. What it shows is that even against that best case, moving the indexes inside the scene graph gains performance rather than costing it, and does so while the application writes and maintains none of the indexing code and the indexes stay live as the graph is updated. VII. C ONCLUSION 

We presented Y GGDRASIL , a layer-first 3D scene graph built from generic nodes, edges, and layers, in which the layer hierarchy is a directed acyclic graph rather than a stack and a typed query interface serves semantic and spatial queries in place, without an intermediate conversion. We in-tegrated it into three published pipelines spanning human tra-jectory prediction, object-goal navigation, and human-aware motion planning, which between them cover downstream-only use, construction and consumption together inside a control loop, and augmentation of a graph that already exists. YGGDRASIL is compatible with the common generation frameworks perception pipelines already rely on, but com-patibility is not optimization. Two gaps remain: chocolate ’s per-room schema was designed by hand, and Y GGDRASIL 

has no concurrency control, since every measurement here is single-threaded. Tuning update and merge paths to the access patterns construction actually produces, inferring schemas automatically, and supporting concurrent readers and writers are our directions for future work.
